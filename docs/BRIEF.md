## 1. What this is and why it exists

An automated FP&A pipeline that analyzes Tesla's quarterly results using only public data. Each time it runs, it:

1. pulls Tesla's financials from SEC filings and its quarterly delivery reports,
2. loads them into a SQL database,
3. builds a driver-based forecast for each past quarter, using only data available before that quarter,
4. compares the forecast to what actually happened and breaks the variance into its drivers,
5. has an AI model (OpenAI) draft the analyst commentary and answers to a fixed set of questions,
6. **checks every number the AI wrote against the database** and flags anything that doesn't match,
7. publishes the results to a static dashboard on GitHub Pages.

**The story it has to tell a hiring manager in 30 seconds:** Jacob knows finance and analytics deeply, *and* he can direct AI agents to automate real analyst work quickly and accurately. He spotted a slow manual workflow (quarterly variance analysis and commentary), chose the right tools, and built a pipeline that does it in minutes and proves its own numbers are right.

**Primary audience:** FP&A and finance hiring managers and recruiters (Tesla FP&A, strategic finance at tech companies). Secondary: technical reviewers who open the repo.

### Goals
- A live, polished dashboard with a single shareable link.
- A pipeline you run with one command that refreshes everything when a new quarter is released.
- Verifiable accuracy: every AI-written figure is traced to a source number, and the dashboard shows that.
- A README good enough to read as a case study on its own.

### Non-goals
- No live chatbot. Visitors never call the AI. Q&A answers are generated by the pipeline and saved.
- No user accounts, no backend server, no database in production (the site is static).
- No stock-price targets, buy/sell views, or valuation of TSLA shares.

### Anti-goals (a failure even if it technically works)
- **Any wrong or invented number shown as fact.** Accuracy beats coverage. If a figure can't be verified, it is flagged or left out.
- **Anything that looks official.** No Tesla logo, wordmark, brand fonts, brand red, or product photos. It must read as an independent analysis.
- **Any non-public information.** Jacob works at Tesla. Use only SEC filings and Tesla's public investor-relations releases. Nothing else.
- **A template look.** It must not look like a default SaaS admin dashboard (see the design section).
- **Exposing the API key**, in the repo, the built site, logs or commit history.

## 4. The pipeline

### Stack (builder's call within this frame)
- Python 3.11+, `uv` or `pip` with a lockfile.
- **DuckDB** as the local analytical database, with SQL in `.sql` files so the SQL work is visible.
- `pandas` for transforms; the official `openai` SDK; `pydantic` for structured AI output; `pytest`.
- One command runs everything: `python -m agent run` (or `make run`). Each stage can also run alone: `ingest`, `model`, `variance`, `narrate`, `verify`, `publish`.

### Stages

**1. Ingest.** Download companyfacts JSON (cached), extract the quarterly series below, and load raw tables. Load `deliveries.csv`. Record the source accession number, filing date and filing URL for every value.

**Store one value per metric, period and filing**, not one value per metric and period. Companyfacts repeats the same period across later filings (comparatives, reclassifications). Rules: **actuals** for quarter Q are the values *as first reported* in Q's own 10-Q (or derived from the 10-K for Q4), which is what the "ties to the 10-Q" ticks point at. **Forecast inputs** are the latest values available on the cutoff date. Note any later restatement in the verification report rather than overwriting.

Quarterly series (use the XBRL tags Tesla actually reports; some may change over time, so map them in one config file and handle gaps):
- Total revenue; automotive sales revenue; automotive regulatory credits; automotive leasing; energy generation and storage revenue; services and other revenue
- Cost of revenues (total and by segment where reported); gross profit
- R&D; SG&A; total operating expenses; operating income
- Net cash from operating activities; capital expenditures (purchases of property and equipment); free cash flow (computed: CFO − capex)
- Deliveries and production (from the manual CSV)

Watch out: 10-K values are annual, so derive Q4 as the annual figure minus Q1–Q3. Cash-flow items in 10-Qs are year-to-date and must be de-cumulated into single quarters. Unit-test both.

**2. Model (driver-based forecast).** For each target quarter Q, the forecast is made at a fixed **cutoff date: the filing date of the previous quarter's 10-Q or 10-K**. That means the model knows last quarter's full results, but *not* Q's delivery report (released a few weeks before Q's 10-Q). This is a "plan made after last quarter closed" view, so deliveries are a real forecast and the volume effect means something. Inputs must be values as they stood on the cutoff date (no look-ahead). Drivers:
- **Deliveries:** a seasonal trend (for example the same quarter last year × recent year-over-year growth). Keep it simple and documented.
- **Automotive ASP** (implied) = automotive sales revenue ÷ deliveries, projected from its recent trend.
- **Automotive sales revenue** = deliveries × ASP.
- **Regulatory credits, energy, services:** recent run-rate with growth.
- **Gross margin** by segment where reported, otherwise total: a recent average.
- **Operating expenses:** recent run-rate growth.
- **Capex:** recent run-rate.

Output forecast P&L lines plus FCF. Also produce **bull, base and bear** scenario versions by flexing deliveries, ASP and gross margin. Use explicit, documented percentages in config.

Track backtest accuracy across all target quarters: absolute % error for revenue, gross profit and operating income, plus the average error. Show these honestly, even when they're bad.

**3. Variance.** For each quarter, compare the actual to the base forecast:
- **Revenue bridge** (forecast → actual), six bars: **volume** (Δdeliveries × forecast ASP), **price/mix** (Δ ASP × actual deliveries), **regulatory credits** Δ, **leasing** Δ, **energy** Δ, **services & other** Δ. It must sum exactly to the total revenue variance. ASP is automotive *sales* revenue ÷ total deliveries. Leased units are included in deliveries, so note this limitation in the methods section.
- **Gross profit bridge:** for each segment shown in the filings, a **volume/revenue effect** (Δsegment revenue × forecast segment margin) and a **margin-rate effect** (Δsegment margin % × actual segment revenue). Group them into bars: automotive, energy, services & other. It must sum exactly to the gross profit variance.
- **Operating income bridge:** gross profit variance, then **R&D** Δ, **SG&A** Δ, and any **restructuring/other** opex Δ (with a sign flip, so higher costs are unfavorable). It must sum exactly.
- **Free cash flow:** a simple two-bar variance, **operating cash flow** Δ and **capex** Δ (higher capex is unfavorable).
- Label each driver favorable or unfavorable.

**4. Narrate (OpenAI).** The AI receives only the computed tables for the quarter, never raw filings and never anything it could invent from. Using structured JSON output, it returns:
- a short analyst-style **variance memo** (about 150–250 words, plain professional tone, no hype, no investment advice),
- **answers to the fixed question set** (below), each 60–120 words,
- for every number it mentions, a **claim object**: `{metric, period, value, unit, sentence_ref}`.

Prompts live in `prompts/` as versioned files. Temperature low.

**Scope per run:** generate a **variance memo for each of the 12 published quarters** (so the quarter picker always shows a memo), and the **Q&A set for the latest quarter only**. Questions 7 and 8 draw on the backtest table across all 12 quarters. When an earlier quarter is selected, the Q&A section says it covers the latest quarter only and offers a link to switch.

**Caching:** key each generated memo and answer set by a hash of its input tables plus the prompt version and model. On a refresh, reuse cached, already-verified text when nothing changed, so past narratives don't shift run to run and cost stays low. Only new or changed quarters call the API. Keep a `--force` flag to regenerate everything.

Fixed question set (per latest quarter unless the question says otherwise; the builder may refine the wording):
1. What drove the revenue variance versus forecast this quarter?
2. Why did gross margin move?
3. How much did regulatory credits contribute, and why does that matter?
4. How did energy storage contribute?
5. What changed in operating expenses?
6. How did free cash flow compare with the forecast, and why?
7. Which driver was hardest to forecast over the last 12 quarters?
8. How accurate has the model been overall?
9. What does the bear scenario assume, and what would it mean for operating income?
10. What would you watch next quarter? (Phrase it as metrics to watch, not predictions.)

**5. Verify.** Code, not AI, checks every claim against the database:
- Exact match after unit and rounding normalization. Tolerance: ±0.5% for currency, ±0.1 percentage points for percentages, exact for unit counts.
- Results: **verified**, **flagged** (mismatch, with the expected value), or **unsupported** (metric not found).
- If anything is flagged or unsupported, re-ask the AI once with the errors. If problems remain, publish anyway, but mark those sentences as flagged on the site. Never silently "fix" a number.
- Also check that the memo contains no buy/sell language or price targets (simple keyword guard).
- Write a verification report per quarter.

**6. Publish.** Write versioned JSON files for the site into `site/public/data/`: quarters, forecasts, scenarios, bridges, memo, Q&A, claims and verification results, backtest accuracy, and run metadata (run time, duration, model, tokens, estimated cost, data as-of date). Commit them, so the static site never needs the API.

### Automation
- GitHub Actions workflow `deploy.yml`: on push to `main`, build the site and deploy to Pages.
- GitHub Actions workflow `refresh.yml`: manual trigger (`workflow_dispatch`), plus an optional schedule turned off by default. It runs the pipeline with `OPENAI_API_KEY` and `SEC_USER_AGENT` from secrets, commits updated data, and then deploy runs.
- Never print secrets; the API key must not appear in logs or built files.

### Tests (must pass in CI)
- XBRL quarter derivation (Q4 from annual; de-cumulating year-to-date cash flow).
- No look-ahead in the forecast: the forecast for quarter Q only uses filings dated on or before the previous quarter's filing date, and no delivery figure for Q itself.
- Bridges sum exactly to total variance.
- Verifier: catches a deliberately wrong number, normalizes units, and handles percentages.
- The publish step produces JSON matching the schema the frontend expects.

## 5. The dashboard: content and flow

A single page, built with Vite, React and TypeScript, deployed as static files to GitHub Pages (set the `base` path for the repo). Charts are custom SVG with D3 scales, because the hero waterfall needs to look bespoke, not like a library default. Data loads from the committed JSON. The latest quarter is shown by default, with a quarter picker to look at earlier ones.

Sections, in the order a hiring manager reads them:

1. **Hero: the latest quarter's revenue bridge.**
   - Headline (sentence case): *"Tesla's quarter, forecast and explained by an agent, checked against the filings."*
   - One line under it: the quarter, the forecast vs actual revenue, the variance in $ and %.
   - The **waterfall bridge** (forecast revenue → volume → price/mix → credits → leasing → energy → services & other → actual revenue) is the centerpiece.
   - Beneath it: the verification seal, e.g. "41 of 41 figures in the commentary tick to the 10-Q". It links to the verification section.

2. **How the agent ran.** A horizontal sequence of the six real stages (ingest → load → forecast → explain → verify → publish), each with its duration from the last run. Numbering is fine here because it's a true sequence. On the right: last run date, total run time, AI cost for the run, and the model used. This is the "I automate workflows" proof.

3. **The analyst memo.** The AI-written variance memo, styled as a memo. Every figure in the text is an inline **tick-marked number** (see design): hover or focus shows the source line, the filing and the verification result. Flagged figures are visibly marked, never hidden.

4. **Forecast and scenarios.**
   - A P&L table for the selected quarter with columns for Forecast, Actual, Variance $ and Variance %. Favorable and unfavorable variances use the variance colors plus a text sign, not color alone.
   - A bull/base/bear toggle that recomputes the forecast columns in the browser from the published drivers. The math must match the Python model exactly; ship a test fixture comparing the two.
   - A small 12-quarter chart of revenue, forecast vs actual.

5. **Ask the analyst.** The ten pre-answered questions as an expandable list. Each answer carries its tick-marked numbers and a source link.

6. **Model accuracy.** The backtest results: error by quarter for revenue, gross profit and operating income, plus the average. Plain and honest, including misses.

7. **How it works and how it's controlled.** A short architecture diagram (simple SVG, not an image of code). It explains what the code does vs what the AI does, the verification rules, the data sources and their limits, and that it uses public data only.

8. **About.** Two or three lines about Jacob: "Built by Jacob Kambour, MS Finance & Analytics, Santa Clara University." Links to GitHub, LinkedIn and résumé; Jacob fills in the URLs in `site/src/config.ts`.

**Footer disclaimer (required):** "Independent analysis built from Tesla's public SEC filings and investor-relations releases. Not affiliated with or endorsed by Tesla, Inc. Not investment advice."

Copy rules: plain sentence-case language, active voice, no hype words ("revolutionary", "supercharged"), no emoji. Empty and error states explain what's missing and what to do (e.g. "No forecast for this quarter: it needs four earlier quarters of history.").

## 6. Visual design

**Concept: the audited workpaper.** In finance, auditors mark every number they've checked with a tick mark that says where it ties. This dashboard borrows that language: the AI writes, the code audits, and the page shows the ticks. That's the one bold idea. Everything else stays quiet, precise and disciplined, the way good finance work looks.

### Palette

| Name | Hex | Use |
|---|---|---|
| Paper | `#F4F6F8` | Page background (cool, not cream) |
| Ink | `#18212B` | Primary text, axis labels |
| Ledger rule | `#CBD3DC` | Table rules, gridlines, borders |
| Forecast cobalt | `#2448C8` | Forecast series, links, focus ring |
| Tied green | `#0E7A5A` | Favorable variance, verified ticks |
| Flag amber | `#A85B00` | Unfavorable variance, flagged figures |

Use white `#FFFFFF` only for the raised table/memo surfaces. Never use Tesla red or anything close to it. Provide a dark mode built from the same hues (Paper ↔ `#121820`, Ink ↔ `#E6EBF0`, lighten cobalt, green and amber enough to pass WCAG AA). All text and chart elements must meet AA contrast. Variance meaning never relies on color alone: always add a sign (+/−) and the word favorable/unfavorable for screen readers.

### Type
- **IBM Plex Sans** for the interface, tables and all numbers. Turn on tabular figures (`font-variant-numeric: tabular-nums`) everywhere numbers appear, so columns line up like a real financial statement.
- **Source Serif 4** only for the AI-written memo and Q&A answers. The serif marks "this is the analyst's narrative" against the sans "this is data". Give it slightly more line-height (about 1.55).
- Type scale: a modest classical scale (about 1.25 ratio); headline around 40–48px desktop, 30px mobile. Line length under 80 characters for prose.
- Don't use: all-caps labels, tracked-out eyebrow labels above headings, monospace for small labels, one accented word in a headline, or `→` appended to links.

### Signature element: tick marks
Every AI-written figure is rendered as a number followed by a small hand-drawn-style tick (SVG):
- **✓ tied** (green): verified against the database. Hover/focus shows "Ties to 10-Q, Q2 2026: Automotive sales revenue $X". Clicking opens the source filing.
- **⚑ flagged** (amber): mismatch. The tooltip shows the expected value.
- **? unsupported** (amber outline): couldn't be traced.

Include a small legend near the memo, like an auditor's tickmark legend. Ticks must be keyboard-focusable, with an accessible label.

### Layout
Left-aligned, single column for prose with a wider canvas for charts and tables. Max content width around 1120px; prose column around 680px. No grid of identical cards. Sections are separated by generous whitespace and a single ledger rule, not by boxes.

### Motion
One orchestrated moment only: on first load, the waterfall bars draw in sequence from forecast to actual (about 1.2s total), and then the verification seal's ticks appear. Nothing else animates on its own. User-triggered transitions (expanding a Q&A, switching scenario) can animate briefly to show what changed. Respect `prefers-reduced-motion`: show the final state instantly.

### Quality floor
- Responsive down to 375px: the waterfall becomes horizontally scrollable or switches to a vertical bridge; tables scroll horizontally with the first column pinned.
- Visible keyboard focus everywhere (cobalt ring).
- Charts have text alternatives: a visually hidden table of the bridge values.
- Lighthouse accessibility ≥ 95 and performance ≥ 90 on the built site.

### Avoid (these read as templated)
Identical rounded cards with soft grey shadows, gradient washes, a near-black page with a neon accent, cream with terracotta, a hero made of one huge number with a tiny label, fade-up animation on every section, emoji, default chart-library styling, middle-dot meta strings ("A · B · C").

## 11. Handoff protocol (required for every agent)

Several agents will work on this repo over time: Grok, the Cursor agents it starts, and Claude Code when Grok's usage runs out. Any of them must be able to stop at any moment, and the next one must be able to pick up without asking Jacob anything. **The repo is the single source of truth.** Nothing important may exist only in an agent's chat history.

### First commit (before any product code)
1. Create the repo with `docs/BRIEF.md` (this file, copied verbatim), `docs/PLAN.md`, `docs/PROGRESS.md`, `docs/DECISIONS.md`, `AGENTS.md`, `CLAUDE.md` and `.cursor/rules/handoff.mdc`.
2. `AGENTS.md` and `CLAUDE.md` contain the same short instruction:
   > Before doing anything, read `docs/BRIEF.md`, `docs/PLAN.md`, `docs/PROGRESS.md` (latest entry first) and `docs/DECISIONS.md`. Follow the handoff protocol in BRIEF section 11. Never commit secrets.
3. `.cursor/rules/handoff.mdc` is an always-applied Cursor rule with the same instruction.

### `docs/PLAN.md`: the build plan
- Break the brief into milestones (M1 setup and data ingest, M2 model and variance, M3 narration and verification, M4 publish and automation, M5 dashboard, M6 README, polish and launch), and each milestone into small tasks. Each task should take one agent session or less.
- Each task gets an ID (`M2-T3`), a one-line goal, its acceptance check (usually a test or command), and a status: `todo`, `in progress (agent name, date)`, `done (commit hash)` or `blocked (reason)`.
- An agent **claims a task** by setting it to `in progress` and pushing that change *before* starting work, so two agents never work on the same task.
- Update the plan when a task finishes or the plan changes. Never delete history; mark superseded tasks as such.

### `docs/PROGRESS.md`: the handoff log
Newest entry at the top. An agent adds an entry **after every finished task and always before stopping**, including when it is about to run out of usage or context. Each entry uses this template:

```
## YYYY-MM-DD HH:MM (timezone) — <agent name: Grok / Cursor agent / Claude Code>
**Task(s):** M2-T3 (done), M2-T4 (in progress)
**What changed:** 2–5 bullets, with file paths
**Current state:** what works now; test status (command + pass/fail count)
**Next step:** the exact next action, specific enough to start immediately
**Blockers / questions for Jacob:** none, or a list
**Notes for the next agent:** gotchas, half-finished work, commands to run first
**Last commit:** <hash> on <branch>
```

Keep a short **"Current status"** block at the very top of the file (above the entries) that is always rewritten: current milestone, % of tasks done, what's next, open blockers, and how to run the project right now.

### `docs/DECISIONS.md`: the decision log
Every non-obvious choice (a library, a formula, an XBRL tag mapping, a change to the brief) gets a dated entry: the decision, the alternatives considered, and why. If an agent must deviate from this brief, it logs the deviation here first. It never silently edits `docs/BRIEF.md`.

### Git rules (to keep multiple agents from colliding)
- One task per branch, named `task/M2-T3-short-name`; open a pull request into `main` and merge once tests pass. Small, frequent commits with clear messages that include the task ID.
- **Never leave work only on a local machine.** Commit and push (to the task branch) before stopping, even if the work is unfinished; say so in PROGRESS.md.
- Pull/rebase from `main` before starting a task.
- `main` must always pass tests.
- Only one agent works on a given task branch at a time; the claim in PLAN.md is the lock.

### Taking over (for any new agent, including Claude Code)
1. Read `AGENTS.md`/`CLAUDE.md`, then `docs/BRIEF.md`, `docs/PLAN.md`, the top of `docs/PROGRESS.md`, and `docs/DECISIONS.md`.
2. Check out the branch named in the last PROGRESS entry, pull, and run the tests to confirm the stated state is real.
3. If a task is marked `in progress` by another agent with no PROGRESS entry for over a day, treat it as abandoned. Note the takeover in PROGRESS.md and continue from that task's branch.
4. Add a PROGRESS entry saying you took over, then continue with "Next step".

### Secrets and safety in handoffs
- Never write API keys, tokens or the SEC contact string into any doc, commit or log. Refer to them only by env var name (`OPENAI_API_KEY`, `SEC_USER_AGENT`).
- Document setup needs in PROGRESS.md as instructions ("Jacob must add `OPENAI_API_KEY` to repo secrets"), never values.
- Don't make the repo public, enable Pages publicly, or change repo settings without Jacob's go-ahead recorded in PROGRESS.md. Stop and list it as a question for Jacob instead.
